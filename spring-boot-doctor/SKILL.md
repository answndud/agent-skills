# Spring Boot Doctor

Run a post-change diagnosis loop for Spring Boot projects. Treat this as a second-pass reviewer after implementation, not as a generic best-practices note. The goal is to catch AI-generated backend regressions that compile locally but are unsafe for production.

Default to Korean output for Korean users. Write the final doctor report in Korean unless the user explicitly requests another language. Keep technical identifiers, commands, file paths, severity labels, and verdict labels in English when that improves precision.

## Core Rule

Do not say "complete" immediately after backend edits. First inspect the diff, classify the changed areas, run the smallest meaningful verification set, score the result, fix P0/P1 issues, rerun relevant verification, and report residual risk.

## Use This Skill

Use this skill after changes to:

- Spring MVC controllers, request/response DTOs, validation, error responses, or API paths.
- Service/domain logic, state transitions, permissions, tenant/role boundaries, or side effects.
- Repository, entity, QueryDSL, JPA mappings, fetch strategies, transactions, or database access.
- Spring Security, JWT, session, cookie, Redis session/cache, CORS, CSRF, OAuth, or auth principal handling.
- Flyway migrations, schema changes, indexes, constraints, enum columns, seed data, or DB profile settings.
- `application.yml`, `application-*.yml`, `.properties`, prod/demo/local profiles, Actuator, Prometheus, OpenAPI/Swagger, Docker, CI, or deployment files.
- Observability, logging, metrics, audit logs, health/readiness, or operational runbooks.
- Spring Boot backend code generated by Codex before commit or PR.

Skip this skill for pure frontend-only edits, simple README wording changes, image/design-only changes, or files clearly unrelated to Spring Boot runtime behavior.

## Doctor Workflow

1. Detect project shape.
2. Inspect diff and classify changed areas.
3. Inspect nearby safety context for the changed surface.
4. Discover targeted tests.
5. Pick the minimal verification commands.
6. Run commands when available.
7. Perform rule checks on the changed areas.
8. Compare against baseline when possible.
9. Score health from 0 to 100 with severity caps.
10. Fix P0/P1 issues before considering the work complete, unless the user requested report-only mode.
11. Rerun relevant verification after fixes.
12. Report baseline/current score, verdict, commands, issues, fixes, and remaining risks.

## Project Detection

Inspect evidence before choosing commands:

```bash
pwd
git status --short
find . -maxdepth 3 -name 'build.gradle*' -o -name 'pom.xml' -o -name 'settings.gradle*'
find . -maxdepth 4 -path '*src/main*' -type d
find . -maxdepth 4 -name 'application*.yml' -o -name 'application*.yaml' -o -name 'application*.properties'
find . -maxdepth 4 -path '*db/migration*' -type f | sort
find docs -maxdepth 3 -type f 2>/dev/null | sort
```

For Gradle, inspect tasks:

```bash
./gradlew tasks --all
```

For Maven, inspect available lifecycle/plugins from `pom.xml` and use `mvn test`, `mvn -DskipTests compile`, or project-specific profiles.

Record:

- Build tool and wrapper path.
- Java and Spring Boot versions.
- Package/module layout.
- Profile files.
- Migration tool.
- Security configuration files.
- Available test tasks.
- Documentation SSOT files such as planning/progress docs, developer guides, environment contracts, API docs, deployment guides, and migration runbooks.

## Diff Classification

Use the current worktree diff by default:

```bash
git diff --name-only
git diff --stat
git diff
```

If the user asks for staged or PR review, use `git diff --cached` or the provided PR diff instead.

Classify every relevant change:

- `api`: controller, route, request/response DTO, validation, exception handler, OpenAPI docs.
- `security`: Spring Security, JWT, session, cookie, Redis session, principal, CORS/CSRF, roles, tenant ownership.
- `persistence`: entity, repository, QueryDSL, transaction, JPA mapping, fetch strategy.
- `migration`: Flyway scripts, schema, indexes, constraints, seed data.
- `domain`: service logic, state machine, invariant, side effects, idempotency, concurrency.
- `config-ops`: profiles, Actuator, Prometheus, Swagger/OpenAPI exposure, Docker, CI, deployment.
- `observability`: logging, metrics, audit, health/readiness, tracing/correlation id.
- `docs`: SSOT docs, runbooks, environment contract, API/deployment docs.

## Changed Surface vs Safety Context

Inspect changed files first, then inspect nearby safety context. Do not stop at the diff when Spring wiring, security rules, transaction boundaries, or API contracts depend on surrounding files.

For `api` changes, also inspect:

- Security configuration and method-security annotations affecting the endpoint.
- Controller advice/global exception handler.
- Request/response DTOs and validators.
- Service method called by the endpoint.
- Existing integration tests for the endpoint family.
- OpenAPI/API docs if present.

For `persistence` changes, also inspect:

- Entity mappings referenced by the query or repository.
- Transaction boundary in the calling service.
- Existing Flyway schema and relevant migration history.
- Tests using the changed repository/query.

For `security` changes, also inspect:

- All endpoints affected by changed matchers or annotations.
- JWT, cookie, session, Redis, CSRF, and CORS configuration.
- Existing authorization tests.
- Prod profile exposure for Swagger/OpenAPI, Actuator, Prometheus, and admin endpoints.

For `migration` changes, also inspect:

- Matching entity/DTO/repository assumptions.
- Existing data assumptions and seed/reference data.
- Deployment docs or migration runbook.

For `config-ops` changes, also inspect:

- Profile-specific overrides.
- Deployment/Docker/CI references to the changed keys.
- Env contract docs.

## Verification Command Selection

Prefer targeted commands first, then broaden only when risk requires it. Do not blindly run every test if a narrower high-signal command exists.

For Gradle projects, prefer:

```bash
./gradlew compileJava compileTestJava
./gradlew test --tests 'fully.qualified.TestClass'
./gradlew fastTest
./gradlew integrationTest
./gradlew performanceSmokeTest
./gradlew bootJar
docker compose config
```

For Maven projects, adapt to:

```bash
./mvnw -DskipTests compile test-compile
./mvnw -Dtest=TestClass test
./mvnw test
./mvnw verify
```

Selection rules:

- Always run compile verification after Java/Kotlin backend code changes when feasible.
- Run targeted tests when changed classes have obvious test classes.
- Run integration tests for controller, security, repository, QueryDSL, migration, or application context changes.
- Run performance smoke tests for query, cache, pagination, N+1, Redis, or critical hot-path changes when available.
- Run `bootJar` or equivalent packaging for deployment/config changes.
- Run `docker compose config` when Docker Compose files changed.
- If a command is unavailable or too expensive for the current turn, mark it as `not run` with the reason. Do not treat unrun verification as passed.

## Test Discovery

Search likely tests before choosing commands. For each changed production class:

```bash
changed='src/main/java/.../SomeService.java'
base=$(basename "$changed" .java)
find src/test -name "${base}Test.java" -o -name "${base}IT.java" -o -name "*${base}*Test.java" -o -name "*${base}*IT.java"
```

Also search by endpoint, domain keyword, table name, or error code:

```bash
rg -n "endpoint-or-domain-keyword|error-code|table_name" src/test || true
```

If relevant behavior changed and no relevant test exists:

- `security`, `repository`, `query`, `migration`, or `domain` changes: record P1.
- `api`, `config`, `cache`, or `observability` changes: record P1 when externally visible or production-sensitive, otherwise P2.
- `docs-only` changes: do not record a test issue unless docs claim behavior changed.

## Regression Policy

When possible, compare current findings against a pre-change baseline or the main branch. Do not hide a regression behind an acceptable absolute score.

- If reviewing a diff, treat newly introduced P0/P1 issues as blocking even when the total score remains `Good`.
- If an issue existed before and is unrelated to the diff, report it under `existing risk` and do not block unless the current change worsens it.
- If no baseline is available, state `baseline unavailable` and score only the current changed surface.
- If baseline is available, report `baseline score`, `current score`, and `regression`.
- If the current change lowers the score because of new P0/P1 findings, block completion.
- Avoid scope creep: do not rewrite unrelated legacy risks during doctor work unless they directly affect the changed surface.

## Severity

Use the highest applicable severity. Be conservative for security, authZ, tenant boundaries, prod exposure, and migrations.

### P0 Blocking

- Compile failure, application context load failure, or core test failure.
- Protected API reachable without required authentication.
- Role, tenant, organization, account, resource, or ownership boundary escape.
- Secret, API key, token, password, private key, or credential leak.
- Swagger/OpenAPI, Actuator, Prometheus, H2 console, or admin endpoint unintentionally exposed in prod.
- Destructive migration without backup, backfill, rollback, or forward-fix plan.
- User, account, billing, membership, workflow, permission, or other core domain data integrity broken.
- OSIV OFF likely causes immediate `LazyInitializationException` in the changed path.

### P1 Major

- Controller request DTO lacks validation for externally supplied fields.
- Service transaction boundary is missing, too broad, not read-only where needed, or placed at the wrong layer.
- Repository, QueryDSL, or entity behavior changed without meaningful test coverage.
- High-risk N+1 query, pagination count issue, or unnecessary DB/cache round trip added.
- API response shape, error response shape, status code, path/version convention, pagination, sorting, or filtering contract drift.
- Domain state transition validation missing.
- Refresh token, session invalidation, cookie, CSRF, CORS, or Redis session consistency policy missing.
- Migration lacks index, default, backfill, lock-risk, or existing-data consideration.
- Profile settings drift across local/demo/prod.
- Performance-sensitive path regressed without smoke coverage.

### P2 Minor

- Test coverage is thin but no critical path is immediately broken.
- Logging lacks request/domain context.
- Docs or runbook update is missing for a behavior/config/API change.
- Naming or package placement obscures responsibility.
- Controller/service/repository boundary is somewhat blurred.
- DTO/entity mapping is duplicated or verbose but safe.

### P3 Polish

- Comment, docs wording, test display name, small naming refinement, or cleanup opportunity.

## Health Score

Start at 100:

- P0: -25 each.
- P1: -10 each.
- P2: -4 each.
- P3: -1 each.

Apply hard caps after subtraction:

- Compile failure: max 49.
- Required test failure: max 59.
- AuthN/AuthZ bypass possibility: max 39.
- Tenant/role/ownership boundary escape possibility: max 39.
- Secret leak: max 39.
- Prod profile dangerous exposure: max 39.
- Destructive migration risk: max 49.
- API contract breaking change without docs/tests: max 69.

Verdict:

- 90-100: Excellent.
- 75-89: Good.
- 60-74: Needs work.
- 40-59: Risky.
- 0-39: Critical.

P0/P1 issues block completion. Fix them or clearly state why they remain unresolved and do not present the work as complete.

## Rule Checks

### Build/Test

- Verify compile and test tasks exist before running.
- Do not ignore failing tests.
- If behavior changed and no test exists, record at least P1 for security/repository/migration/domain changes, otherwise P2.
- Prefer targeted tests, then `fastTest`, then `integrationTest` when risk requires.
- Rerun affected verification after fixes.

### API/Controller Contract

Check:

- `/api/v1` or project-specific path/version convention is preserved.
- Controllers do not return JPA entities directly.
- Request DTOs use validation annotations and controller parameters use `@Valid` where needed.
- Response DTO shape, error shape, status codes, pagination, sorting, and filters are unchanged unless explicitly intended.
- Create/update/delete idempotency and side effects are clear.
- OpenAPI/Swagger and API docs are not stale after contract changes.

### Security/AuthZ/Tenancy

Check:

- Endpoint authentication is explicit.
- Spring Security 6 `SecurityFilterChain` matcher order is specific before broad and deny-by-default where practical.
- `requestMatchers(...).permitAll()` is narrowly scoped and not accidentally covering protected APIs.
- Method security such as `@PreAuthorize`/`@PostAuthorize` is present where URL-level rules are insufficient.
- Role checks match project-specific domain roles such as admin, owner, manager, member, operator, or viewer.
- Principal is obtained from a trusted security context, not blindly from request body/query params.
- `SecurityContextHolder` direct usage is justified, testable, and not bypassing injected/authenticated principal patterns.
- Request-supplied ids such as `userId`, `accountId`, `resourceId`, `tenantId`, or `organizationId` are ownership-checked before use.
- JWT, cookie, session, refresh-token rotation/invalidation, Redis session consistency, CSRF, CORS, `SameSite`, `Secure`, and `HttpOnly` settings are safe.
- Stateless JWT settings and Spring session policy do not contradict each other.
- `csrf.disable()` has a clear API/session rationale and does not weaken browser cookie flows.
- CORS does not combine wildcard origins with credentials.
- Tokens, passwords, private data, or secrets are not logged.
- Prod profile fails closed for Swagger/OpenAPI, Actuator, Prometheus, admin endpoints, and debug features.
- Spring Boot 3 / Jakarta imports are not mixed with legacy `javax.*` APIs in changed code.

### Persistence/JPA/Transaction

Assume Open Session In View is OFF unless proven otherwise.

Check:

- Lazy associations are not accessed outside transaction/service boundaries.
- `@Transactional` belongs on service/application boundaries, with `readOnly = true` for read paths where appropriate.
- Fetch join, entity graph, projection, batch size, or DTO query is used where lazy access or N+1 risk exists.
- QueryDSL queries do not accidentally create N+1, duplicate rows, broken pagination, or expensive count queries.
- Bulk update/delete clears or avoids stale persistence context.
- `equals`, `hashCode`, `toString`, JSON serialization, logs, or DTO mapping do not traverse lazy associations.
- Cascade, orphan removal, soft delete filters, optimistic locking, and entity lifecycle hooks are safe for the changed domain.
- Controllers do not serialize entities.

### Migration/Database Safety

Check:

- Flyway naming follows project convention.
- Entity schema and migration schema match.
- Destructive changes have backup/backfill/rollback or forward-fix strategy.
- `NOT NULL` additions include default/backfill strategy for existing data.
- Large-table changes consider lock risk.
- New filters/joins have necessary indexes.
- Unique constraints account for existing duplicate data.
- Foreign key cascade and orphan effects are intentional.
- Enum/string changes remain backward compatible where old app versions or data may exist.
- Local/demo/prod DB config drift is not introduced.

Classify each migration:

- `additive`: new table/column/index that preserves old behavior.
- `backfill`: data population or repair.
- `constraint tightening`: new `NOT NULL`, `UNIQUE`, FK, check constraint, or stricter enum/value rules.
- `destructive`: drop, rename, truncate, irreversible type change, or lossy data rewrite.
- `data rewrite`: update/transform existing rows.
- `index-only`: index add/drop/change.
- `seed/reference-data change`: seed, demo, lookup, or reference data.

Migration compatibility rules:

- Prefer expand-and-contract for risky schema changes.
- Do not add a non-null column without default/backfill or a two-step deployment plan.
- Do not rename/drop columns in one step unless all app versions are coordinated.
- Flag long lock, table rewrite, or large-table migration risk.
- For unique constraints, require a duplicate detection query or a documented no-duplicate assumption.
- For seed/reference-data changes, check idempotency and environment scope.
- Treat destructive migration uncertainty as blocking until proven safe.

### Domain State Machine

Check:

- Approval, rejection, invitation, subscription, order, membership, role assignment, payment, or other state transitions reject illegal transitions.
- Duplicate requests are idempotent where needed.
- Concurrency/race conditions are considered.
- Audit log, notification, event, or cache invalidation side effects are not skipped.
- Domain invariants live in service/domain layer, not only controller validation.

### Error Handling

Check:

- Global exception handler keeps response format stable.
- Validation errors have consistent shape.
- Domain exceptions map to stable error codes/statuses.
- Expected errors do not become generic 500 responses.
- Stack traces/internal details are not exposed to users.
- User-facing messages and internal logs are separated.

### Observability/Operations

Check:

- Important commands, events, permission changes, and security-sensitive actions have audit logs where appropriate.
- Logs include useful context without leaking secrets or private data.
- Metrics are added or preserved for operationally important paths.
- Health/readiness, Actuator, Prometheus scrape path, graceful shutdown, cache/session behavior, and seed data remain safe per profile.
- Slow query/cache miss risks are called out.

### Documentation Drift

If docs SSOT exists, check whether changes require updates to:

- `docs/PLAN.md`
- `docs/PROGRESS.md`
- `docs/COMPLETED.md`
- Developer guide
- Environment contract
- API docs
- Deployment guide
- Migration/runbook
- Environment variable contract

Record stale docs as an issue. For API/security/config/migration changes, missing docs are usually P1 or P2 depending on risk.

## Evidence Standard

Every issue must cite concrete evidence. Acceptable evidence includes:

- Changed file path and relevant class, method, symbol, or config key.
- Command failure and short output summary.
- Missing test evidence from test discovery.
- Migration file name and operation type.
- Endpoint path and role/tenant/ownership boundary.
- Profile file and exposed setting.
- Documentation file that should be updated.

Avoid vague findings such as "security may be weak" without a concrete file, endpoint, rule, missing test, or missing verification.

## Fix Policy

- Prefer narrow, evidence-backed fixes.
- Avoid broad rewrites during doctor work.
- Fix P0/P1 before finalizing unless the user explicitly asks for report-only mode.
- For P2/P3, fix if localized and low risk; otherwise report as follow-up.
- After any fix, rerun the relevant command or state why it was not rerun.
- Do not ask the user to decide before best-effort diagnosis; continue with available evidence.

## Report-only Mode

If the user explicitly asks for review, audit, assessment, feedback, or report only, do not edit files.

- Still run best-effort diagnosis, scoring, and command selection.
- Mark P0/P1 as blocking recommendations instead of applying fixes.
- Include concrete fix recommendations and the exact verification that should pass after fixes.
- Do not convert a report-only request into implementation unless the user explicitly asks.

## Forbidden Behavior

- Do not claim "no issues" without running or explaining verification.
- Do not complete with compile failures.
- Do not downgrade security/authZ warnings to "later".
- Do not approve DB migration risk without checking data/backfill/rollback implications.
- Do not pass API response shape changes without docs/tests.
- Do not leave dev convenience settings open in prod.
- Do not assume request-provided ids are authorized.
- Do not assume OSIV saves lazy loading issues.
